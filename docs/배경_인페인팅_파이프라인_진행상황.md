# "내 사진으로 나만의 배경 만들기" (custom_photo_bg) — 진행상황

이 문서는 "사용자가 업로드한 원본 사진을 그대로 애니메이션 배경으로 만들어주는" 새 유료
기능(배경_인페인팅_파이프라인) 작업의 실시간 작업 로그이자 상태판입니다. 새 단계를
완료할 때마다 이 문서를 갱신합니다.

> 이 기능은 강아지 누끼(전경) 파이프라인이나 LivePortrait 액션 20종 파이프라인과는
> 완전히 별개입니다. `backend/routers/generate.py`, `backend/services/seamless_loop_service.py`
> 내부, `backend/services/live_portrait_*`, `backend/workers/live_portrait_worker.py`,
> `backend/scripts/test_live_portrait_goya.py`는 다른 에이전트가 소유하고 있어 이번
> 작업에서 **읽기만 하고 수정하지 않았습니다**.

## 전체 아키텍처 요약

```
[FastAPI] POST /api/background-video/generate  (multipart: 원본 사진 파일)
   → Supabase Storage에 원본 사진 업로드
   → background_video_jobs 테이블에 status='queued' 행 insert
   → 즉시 job_id 반환

[로컬 RTX 4090 머신] python -m backend.workers.background_video_worker
   → status='queued'(또는 stale 'running') 행을 polling으로 claim
   → (1) SAM2 역마스크(vitmatte_service의 SAM2 로더 재사용) + LaMa 인페인팅
        → 강아지가 지워지고 자연스럽게 채워진 배경 이미지
   → (2) 인페인팅된 배경 이미지를 Supabase에 업로드해 공개 URL 확보
   → (3) Luma I2V로 배경 앰비언트 모션 영상 생성(새 프롬프트, 최대 2회 재시도)
   → (4) seamless_loop_service.make_seamless_loop_mp4()를 블랙박스로 호출(내부 수정 없음)
   → (5) ffmpeg로 fps/duration을 강아지 영상 규칙에 맞춰 강제 동기화
   → (6) 최종 mp4를 Supabase Storage에 업로드 + status='done'
   → 매 단계마다 background_video_jobs.progress_json 갱신(폴링용)

[FastAPI] GET /api/background-video/jobs/{job_id} → 진행률/결과 조회 (프론트 polling용)

[프론트] theme-selection-screen.tsx에서 "내 사진으로 나만의 배경" 카드 선택
   → custom-background-screen.tsx (생성 대기 + 폴링 UI)
   → 완료되면 payment-screen.tsx (기존 PayPal 플로우, 수정 없이 재사용)
```

## 단계별 상태

### 1단계 — LaMa vs Stable Diffusion Inpainting 조사/결정
- 상태: ✅ 완료
- 결론: **LaMa 채택** (Stable Diffusion Inpainting 사용 안 함)
- 근거:
  - 이 유스케이스는 "이미 있던 사물(강아지)을 지우고 그 자리를 배경 텍스처로 자연스럽게
    메꾼다"(object removal inpainting)이지, 텍스트 프롬프트로 새 콘텐츠를 창작하는
    게 아님 — LaMa(advimman/lama)가 정확히 이 문제만을 위해 만들어진 순수 CNN
    (Fourier Convolution) 기반 모델.
  - 라이선스: **Apache-2.0** — 코드/체크포인트 모두 상업적 이용 가능.
  - 모델 크기: big-lama 체크포인트 ~200MB대 — SD Inpainting(UNet+VAE+텍스트 인코더
    포함 수 GB)보다 훨씬 작음.
  - 텍스트 프롬프트 불필요 — "무엇을 그릴지"가 아니라 "주변 텍스처로 구멍만 메꾸면"
    되므로, SD의 프롬프트 기반 생성 능력은 오히려 엉뚱한 사물이 배경에 생성될 리스크로
    작용.
  - 속도: CNN 순전파 1회로 끝나 SD의 반복 디퓨전 스텝(수십 회)보다 훨씬 빠름 — 공식
    이슈들에서 CPU 동작도 확인되나, 우리는 로컬 RTX 4090에서 실행하므로 속도는 문제
    안 됨.
  - `simple-lama-inpainting`(PyPI, Apache-2.0) pip 패키지로 별도 리포 clone 없이 통합
    가능(LivePortrait처럼 무거운 서브프로세스 통합이 필요 없음).
- 상세 근거는 `backend/services/background_inpaint_service.py` 상단 docstring에 기록.

### 2단계 — 전경/배경 분리 + 인페인팅
- 상태: ✅ 완료 (코드 작성 완료, GPU 미보유 환경이라 실제 추론 미검증)
- 파일: `backend/services/background_inpaint_service.py`
- 한 일:
  - `vitmatte_service`의 `_detect_subject_bbox`/`_expand_bbox`/`_sam2_mask`/
    `_grabcut_mask`/`_get_device`를 그대로 import해서 재사용 — 새 SAM2 로딩 코드를
    만들지 않음(요청사항 그대로).
  - SAM2 마스크를 역(inverse)으로 뒤집는 대신, "강아지 이진 마스크"를 dilate해서
    "메꿔야 할 구멍" 마스크를 직접 만드는 방식 채택 — 순수 반전만 쓰면 털 경계에
    얇게 강아지 잔상이 남을 수 있어 여유 마진을 둠(`BACKGROUND_INPAINT_MASK_DILATE_PX`,
    기본 20px). `live_portrait_postprocess.py`가 같은 이유로 마스크를 dilate하는
    것과 동일한 트레이드오프.
  - SAM2 실패 시 GrabCut으로 자동 폴백(`BACKGROUND_INPAINT_SEGMENTER` 환경변수로
    강제 선택도 가능) — vitmatte_service의 기존 폴백 관례와 동일.
  - `inpaint_background_from_photo(image_bytes)` → (인페인팅된 PNG bytes, 진단 메타)
    반환. 진단 메타에 `hole_area_fraction`(구멍이 전체 이미지의 몇 %였는지) 포함 —
    나중에 결과 품질 이상 감지에 활용 가능.

### 3단계 — Luma 배경 앰비언트 모션
- 상태: ✅ 완료 (코드 작성 완료, 실제 Luma API 호출 미검증 — API 키/네트워크 필요)
- 파일: `backend/services/luma_prompts.py` (프롬프트 추가), `backend/services/
  background_video_pipeline.py` (호출부)
- 한 일:
  - `LUMA_ACTION_PROMPTS["IDLE"]`과 같은 스타일(고정 카메라 + 미세 모션 + 반복
    가능)로 `LUMA_BACKGROUND_AMBIENT_PROMPT` 신규 작성 — 대상이 강아지가 아니라
    배경 자체이므로 `LUMA_SUBJECT_RULE`(강아지 1마리만 애니메이션)은 붙이지 않고,
    대신 "강아지/사람/손 등장 금지"를 프롬프트 자체에 명시 + 기존 `LUMA_AVOID_CLAUSE`도
    그대로 유지.
  - 재시도 시 카메라 흔들림/강아지·사람 재생성 오검출을 줄이기 위한
    `LUMA_BACKGROUND_STATIC_CAMERA_BOOST` 보강 문구 추가, `build_background_ambient_prompt
    (retry_boost=True)`로 노출.
  - `background_video_pipeline.py`에서 최대 2회(`BACKGROUND_VIDEO_LUMA_MAX_RETRIES`)
    재시도 — 결과 URL이 `.mp4`로 끝나지 않으면(Luma가 실패 응답을 준 경우) 재시도,
    모두 실패하면 예외를 올려 잡을 `failed`로 기록.

### 4단계 — Seamless loop + fps/duration 동기화
- 상태: ✅ 완료
- 파일: `backend/services/background_video_sync.py` (신규), `backend/services/
  background_video_pipeline.py` (호출부)
- 한 일:
  - **seamless loop**: `seamless_loop_service.make_seamless_loop_mp4()`를 블랙박스로만
    호출 — 내부 구현은 전혀 건드리지 않음(다른 에이전트가 Render 512MB 인스턴스 OOM
    이슈를 조사/수정 중인 바로 그 함수). 이 파이프라인은 로컬 RTX 4090 워커에서만
    실행되므로 그 OOM 리스크 자체가 적용되지 않음.
  - **fps/duration 동기화 규칙 확정**: fps=24(고정), duration=4.0초(기본값) —
    `live_portrait_postprocess.py`가 이미 `cap.get(cv2.CAP_PROP_FPS) or 24.0`로 24를
    fallback으로 쓰고 있어 프로젝트 안에서 암묵적으로 쓰이던 숫자와 맞췄고, duration은
    Luma idle 루프 관례(`SEAMLESS_LOOP_MAX_SEC` 기본 4.0초)를 그대로 가져옴 — "배경도
    계속 반복 재생되는 대기 레이어"라는 성격이 idle 루프와 같기 때문.
  - 이 값은 고정값이 아니라 **기본값**: `sync_video_fps_duration()`/enqueue API 모두
    `target_fps`/`target_duration_sec` 파라미터를 노출해서, 나중에 실제 LivePortrait
    액션 영상의 정확한 fps/길이를 알게 되면 그 값으로 다시 맞출 수 있음. LivePortrait
    쪽 실제 드라이빙 영상이 아직 준비되지 않은 상태라(다른 에이전트 담당), 지금은 정확한
    숫자를 알 방법이 없어 기본값만 정의해 둠 — **사용자가 실제 드라이빙 영상 fps/길이를
    확정하면 이 기본값을 그 값으로 바꿔야 함**.
  - ffmpeg로 `-r`(fps 강제), 원본이 목표보다 짧으면 `-stream_loop`로 반복 후 `-t`로
    정확히 컷 — 원본이 더 길면 단순히 `-t`로 자름.

### 5단계 — 렌더링 타겟 확인 (Unity 언급 관련)
- 상태: ✅ 완료(조사만, 코드 변경 없음)
- 조사 결과: 이 저장소는 **Unity를 쓰지 않습니다.** 현재 라이브 렌더링 타겟은 두 곳:
  1. **웹 앱**(`src/components/memorial/holographic-background.tsx`,
     `theme-background-video.tsx`, `memorial-device-play-screen.tsx`) — CSS/HTML
     `<video>` 레이어 합성이라, 알파 합성이 아니라 **레이어를 겹쳐서(z-index/블렌드
     모드) 보여주는 방식**. 여기서는 배경 영상과 강아지(투명 배경 PNG/webm) 두
     `<video>`/`<img>`를 같은 컨테이너에 겹쳐 그리는 정도로 충분 — fps/duration이
     완전히 똑같지 않아도 시각적으로 크게 어긋나 보이진 않지만, 이번 요청대로 정확히
     맞춰 둠(자연스러운 루프를 위해).
  2. **C++ `device-renderer`**(신설 중, `device-renderer/src/renderer/
     video_layer_renderer.cpp` 등) — 실제 Pepper's-ghost 스타일 기기에서 도는
     별도 렌더러로, 여기가 진짜 알파 합성이 필요한 지점(`asset_type.h`/
     `renderer_factory.cpp` 참고). 이번 작업 범위에서는 `device-renderer`의 C++
     코드를 건드리지 않았음 — 이 파이프라인이 만드는 mp4가 fps/duration만 규칙대로
     나오면, device-renderer 쪽 합성 로직은 그 규칙을 그대로 소비할 수 있음(별도
     연동 작업 필요, 아래 "남은 작업" 참고).
- Unity 관련 파일/레퍼런스는 저장소에서 찾지 못함(`themes.ts` 주석에 "Unity
  light_rgb/snow_forest와 동일 소스"라는 문구만 남아있음 — 과거 자산 출처를 가리키는
  주석으로 보이며, 실제 Unity 프로젝트나 빌드는 이 저장소에 없음). **Unity 쪽 지원은
  만들지 않았습니다** — 필요하면 알려주세요.

  `live_portrait_worker.py`는 다른 에이전트가 동시에 수정 중이라 그 파일을 건드리면
  병합 충돌 위험이 큼. CRUD 함수 이름/시그니처, 클레임(낙관적 잠금) 방식, 내결함성
  정책은 모두 `action_video_jobs.py`와 동일하게 맞춰 일관성을 유지.
- 내결함성: `action_video_jobs`/`live_portrait_worker`와 동일 — 잡 처리 예외는 절대
  워커 루프를 죽이지 않고 `mark_failed`로 기록, SIGINT/SIGTERM으로 안전 종료, stale
  `running` 잡은 `BACKGROUND_VIDEO_STALE_MINUTES`(기본 30분) 후 재클레임.

## 실행 방법 (요약)

```bash
# 0) 최초 1회: Supabase SQL Editor에서 마이그레이션 실행
#    supabase/migrations/20260721000100_background_video_jobs.sql

# 1) 로컬 RTX 4090 머신에 의존성 설치 (LaMa 체크포인트는 최초 추론 시 자동 다운로드)
```

## 남은 작업 (사용자가 해야 하는 것)

1. `pip install -r backend/requirements.txt`로 로컬 RTX 4090 워커 머신에
   `simple-lama-inpainting` 설치(최초 실행 시 big-lama 체크포인트 ~200MB대 자동 다운로드
   — 인터넷 필요).
2. Supabase SQL Editor에서 `supabase/migrations/20260721000100_background_video_jobs.sql`
   실행.
3. 워커 실행 환경에 `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/`LUMA_API_KEY` 등이
   설정돼 있는지 확인(`backend/env.local.example`의 새 섹션 참고).
4. `python -m backend.workers.background_video_worker` 상시 실행(LivePortrait
   워커와 동시에 같은 머신에서 돌려도 서로 다른 테이블만 봐서 간섭 없음).
5. 실제 사진으로 엔드투엔드 테스트(SAM2 인페인팅 품질, Luma 프롬프트 결과, seamless
   loop, fps/duration) — 이 세션은 GPU가 없어 실제 추론 결과를 눈으로 확인하지
   못했습니다. 특히 LaMa 결과 품질(예: 복잡한 배경에서 구멍이 너무 크면 부자연스러운
   결과가 나올 수 있음)은 실제 사진들로 확인 후 `BACKGROUND_INPAINT_MASK_DILATE_PX`
   등을 조정할 필요가 있을 수 있음.
6. LivePortrait 액션 영상의 실제 fps/duration이 확정되면(다른 에이전트 작업 완료 후),
   `BACKGROUND_VIDEO_TARGET_FPS`/`BACKGROUND_VIDEO_TARGET_DURATION_SEC` 기본값을 그
   값으로 맞추거나, enqueue 시 `target_fps`/`target_duration_sec`를 명시적으로 전달.
7. (선택, 필요 시) `device-renderer`(C++ 기기 렌더러) 쪽에서 이 새 배경 영상을 실제
   알파 합성 파이프라인에 연동하는 작업은 이번 범위에 포함하지 않음 — 필요하면 별도
   요청.
8. `theme-thumbs/custom_photo_bg.jpg` 썸네일 이미지 준비(현재는 경로만 참조, 실제
   파일 없음 — 없어도 앱이 깨지진 않지만 카드에 빈 배경이 보임).

## 열린 결정사항 / 트레이드오프 로그

- **LaMa vs SD Inpainting**: LaMa 채택(1단계 참고) — object-removal 유스케이스에
  프롬프트 기반 생성이 불필요/위험하고, 라이선스·크기·속도 모두 LaMa가 유리.
- **큐 구현**: `action_video_jobs`를 확장하지 않고 자매 테이블(`background_video_jobs`)
  + 별도 워커로 분리 — 산출물 스키마가 근본적으로 다르고, 다른 에이전트가 동시에
  `action_video_jobs.py`/`live_portrait_worker.py`를 수정 중이라 병합 충돌을 피하기
  위함.
  - **렌더링 타겟**: Unity는 이 저장소에 없음(과거 자산 출처 주석만 남아 있음) —
  현재는 웹 앱(HTML/CSS 레이어 합성) + 신설 중인 C++ `device-renderer`(실제 알파
  합성) 두 곳이 타겟. 이번 작업은 두 곳 모두가 소비할 수 있는 "fps/duration이 맞춰진
  mp4"를 만드는 데까지만 다루고, `device-renderer` C++ 통합 자체는 하지 않음.
- **fps/duration 기본값(24fps/4.0초)**: LivePortrait 실제 드라이빙 영상이 아직
  없어 정확한 값을 알 수 없는 상태에서 내린 임시 기본값 — 프로젝트 내 기존 fallback
  값(24fps)과 idle 루프 관례(4.0초)에서 근거를 가져왔으나, 실제 값이 확정되면
  갱신 필요.
- **가격**: 기존 프리미엄 테마와 동일한 $2.99 — 별도로 더 받을 근거(예: 추가 GPU
  비용)가 있을 수 있으나, 사용자가 명시하지 않아 기존 티어를 그대로 따름.
